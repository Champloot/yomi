# Участие в разработке

## Перед коммитом

```bash
make check     # форматирование + clippy + тесты
```

или вручную:

```bash
cargo fmt --all
cargo clippy --all-targets -- -D warnings
cargo test
```

CI прогоняет то же самое, но локально это занимает секунды, а не минуты.

## Стиль кода

- Форматирует `cargo fmt`, спорить с ним не нужно.
- `clippy` без предупреждений. Если правило мешает по делу — подавляем
  точечно с `#[allow(...)]` **и комментарием почему**, а не глобально.
- Комментарии отвечают на «почему», а не «что». Что делает код, видно
  из кода; почему выбран именно этот путь — нет.
- Публичные элементы документируются через `///`.
- `unwrap()` и `expect()` — только там, где невозможность паники очевидна
  из соседних строк. В `expect()` пишем осмысленный текст.

## Тесты

- Модульные тесты — в том же файле, в `#[cfg(test)] mod tests`.
- Каждое исправление ошибки сопровождается тестом, который её ловит.
- Тесты не должны трогать домашний каталог: для этого есть
  `YOMI_CONFIG_DIR` и соседние переменные.
- Тесты, ходящие в сеть, помечаются `#[ignore]`.

Пример пользы: тест `cli_definition_is_valid` при первом же запуске
обнаружил, что короткий флаг `-c` был занят одновременно глобальным
`--config` и `--chapters`. Пользователь увидел бы панику при запуске.

## Коммиты

Используем [Conventional Commits](https://www.conventionalcommits.org/ru/):

```
feat(viewer): вывод изображений через протокол kitty
fix(config): не падать на пустом файле конфигурации
docs(adr): решение о поддерживаемых форматах
refactor(core): вынести реестр источников в отдельный модуль
test(source): проверка разбора ответа поиска
chore(deps): обновить clap до 4.5
```

Область (`viewer`, `config`, `core`, `cli`, `db`, `source`) — не
обязательна, но помогает читать историю.

## Ветки

- `main` — всегда собирается и проходит тесты.
- Работа — в ветках `feat/...`, `fix/...`, `docs/...`.

## Архитектурные решения

Меняете что-то заметное — заводите запись в `docs/adr/`. Формат:
контекст, решение, последствия. Одна страница. Принятые записи не
переписываются: если передумали, добавляется новая со ссылкой на старую.

## Границы, которые нельзя нарушать

1. `yomi-core` не знает о терминале. Ни `println!`, ни `clap`,
   ни вывода изображений.
2. `yomi-core` не зависит от `yomi`. Никогда.
3. Новый источник не требует правок в ядре.

Если для задачи приходится нарушить одно из правил — скорее всего, задача
решается не там. Обсудите в issue до написания кода.
