# Архитектура

## Главный принцип

**Ядро ничего не знает о терминале, интерфейс ничего не знает о сети.**

Из этого следует правило зависимостей, которое нельзя нарушать:

```
yomi-cli ──> yomi-viewer ──> yomi-core
yomi-cli ──> yomi-db     ──> yomi-core
yomi-cli ──> yomi-download ──> yomi-core
Обратных стрелок нет и быть не должно.
```

Проверить легко: если в `yomi-core` появился `println!`, `stdout`, `clap`
или что-то про рендеринг — правило нарушено. В `yomi-core` нет ни одного
макроса печати, и это не случайность. Для `yomi-viewer` правило мягче:
он знает про терминал (это его работа), но не знает про `clap` и разбор
аргументов.

Зачем: ровно то же ядро потом обслужит TUI (этап M4), а при желании —
фоновой демон или веб-интерфейс. Если логика расползётся по командам CLI,
TUI придётся писать копипастой.

## Текущая структура

```
yomi/
├── crates/
│   ├── yomi-core/         ЯДРО — модель, конфиг, пути, ошибки
│   ├── yomi-viewer/       ОТОБРАЖЕНИЕ — картинки, терминал, структура файла
│   │   ├── archive.rs     источник страниц: каталог, CBZ, картинка
│   │   ├── capability.rs  определение протокола терминала
│   │   ├── comicinfo.rs   разбор ComicInfo.xml, включая закладки
│   │   ├── structure.rs   том или глава, границы глав
│   │   ├── scan.rs        обход каталога библиотеки
│   │   ├── reader.rs      интерактивный цикл чтения
│   │   └── render/        kitty и юникод-блоки
│   ├── yomi-db/           ХРАНИЛИЩЕ — SQLite, миграции, прогресс, отметки
│   ├── yomi-download/     СБОРКА — упаковка CBZ, разбор имён, метаданные
│   │   ├── parse.rs       том, глава и название из имени файла
│   │   ├── package.rs     запись CBZ, ComicInfo.xml, закладки
│   │   └── naming.rs      имена выходных файлов
│   └── yomi-cli/          ПРИЛОЖЕНИЕ — бинарник `yomi`
├── docs/
└── flake.nix
```

Крейт `yomi-download` назван по прежней задаче — загрузке из сети. Сейчас
он занимается сборкой и упаковкой; переименование отложено, чтобы не
конфликтовать с веткой `net`, где сетевой код продолжает на него
опираться.

## Три границы, которые держат проект

**Ядро не знает о терминале.** Признак нарушения виден при беглом
чтении: в `yomi-core` нет ни одного макроса печати.

**Читалка не знает о хранилище.** Отметки глав приходят в неё через
трейт `ChapterMarks`, а реализацию поверх базы даёт приложение. Иначе
`yomi-viewer` потянул бы за собой SQLite.

**Сборка не знает об источниках.** Метаданные для `ComicInfo.xml`
описываются структурой `PackMeta`, а не главой из трейта `Source`. Без
этого упаковка была бы недоступна для главного случая — папки сканов,
собранной пользователем вручную.

## Крейт `yomi-viewer`

Прячет две разные неприятные реальности сразу:

| Модуль | Что прячет |
|---|---|
| `archive` | различия между каталогом, CBZ и одиночным файлом |
| `natural_sort` | то, что лексикографический порядок имён файлов неверен |
| `capability` | зоопарк графических протоколов терминалов |
| `render/kitty` | формат escape-последовательностей и разбиение на чанки |
| `render/blocks` | приближение картинки символами и ANSI-цветом |
| `reader` | сырой режим терминала, клавиши, перерисовку |

Ключевое решение: `capability::detect` принимает срез переменных
окружения, а не читает их сам. Без этого определение протокола
невозможно протестировать: тесты гоняются параллельно и делят одно
окружение процесса, а подмена глобальных переменных из теста —
источник плавающих падений.

Аналогично `render::blocks::render` возвращает `String`, а не пишет
в stdout: результат можно проверить тестом, не имея терминала.

## Как это вырастет дальше

| Крейт | Когда | Что спрячет |
|---|---|---|
| `yomi-tui` | M8 | ratatui, обработку клавиш, компоновку |
| `yomi-source-*` | заморожено | сетевые API, лимиты, форматы ответов |

Сетевой крейт `yomi-source-mangadex` существует, но только в ветке
`net`: из основной сборки он исключён вместе с загрузкой.

Выделяем в отдельный крейт, когда появляется тяжёлая зависимость
(`reqwest`, `rusqlite`, `ratatui`): это ускоряет пересборку и не даёт
зависимости просочиться туда, где её быть не должно. Так и появился
`yomi-viewer`: `image`, `zip` и `crossterm` не должны быть видны из ядра.

## Точка расширения: источники

`Source` — единственный трейт, который нужно реализовать, чтобы добавить сайт.
Ядро работает с `Arc<dyn Source>` и не знает конкретных типов.

```rust
#[async_trait]
pub trait Source: Send + Sync {
    fn id(&self) -> SourceId;
    fn name(&self) -> &str;
    fn capabilities(&self) -> Capabilities;
    async fn search(&self, query: &SearchQuery) -> Result<SearchResult>;
    async fn manga(&self, id: &str) -> Result<Manga>;
    async fn chapters(&self, manga_id: &str) -> Result<Vec<Chapter>>;
    async fn pages(&self, chapter_id: &str) -> Result<Vec<Page>>;
}
```

`Capabilities` — не украшение. Без него интерфейс будет предлагать фильтр
по автору там, где источник его не поддерживает, и молча возвращать мусор.
Команда `search` уже сейчас предупреждает, когда фильтр будет проигнорирован.

Подробности — [sources.md](internal/sources.md).

## Поток данных при поиске

```
аргументы CLI
   ↓  cli.rs — разбор и валидация
SearchArgs
   ↓  commands/search.rs — преобразование в доменный тип
SearchQuery                     ← ядро уже не знает про командную строку
   ↓  Registry::get(id)
Arc<dyn Source>
   ↓  source.search(&query).await
SearchResult
   ↓  commands/search.rs — форматирование
stdout
```

Ключевой момент: `SearchQuery` — доменный тип, а не структура аргументов
`clap`. Благодаря этому TUI сможет собрать тот же запрос из формы,
а тесты — вручную, без разбора командной строки.

## Обработка ошибок

Разделение, принятое в экосистеме Rust:

- **`yomi-core` использует `thiserror`** — перечисление `Error` с точными
  вариантами. Вызывающий код может разобрать ошибку по вариантам.
- **`yomi` использует `anyhow`** — приложению не нужно различать все
  типы ошибок, ему нужен контекст для пользователя. `.context("...")`
  добавляет пояснение к цепочке.

Связывает их `exit::Code::from_error`: он делает `downcast_ref` до
`yomi_core::Error` и выбирает код возврата. Так текст ошибки остаётся
человеческим, а код — машиночитаемым.

## Потоки и асинхронность

Рантайм `tokio` создаётся в `main` вручную, а не через `#[tokio::main]`.
Причина: явный код видно и легко ограничить число рабочих потоков, когда
дойдут руки до слабых машин и Raspberry Pi.

Асинхронность нужна ради загрузки: десятки страниц качаются параллельно,
и блокировать поток на каждом запросе расточительно. Трейт `Source`
асинхронный с самого начала намеренно — переделывать синхронный трейт
в асинхронный потом больно, а стоимость решения сейчас нулевая.
