# Ежедневная работа

## Цикл разработки

```bash
nix develop            # или автоматически, если настроен direnv
cargo check            # быстрая проверка компиляции — основной инструмент
cargo test             # перед каждым коммитом
make check             # то же, что проверит CI: формат + линтер + тесты
```

`cargo check` в разы быстрее сборки. Пишите код короткими итерациями
«написал — проверил», а не «написал 300 строк — собрал».

## Git

Проект ещё не под контролем версий. Первым делом:

```bash
git init
git add .
git commit -m "feat: каркас проекта (M0)"
git branch -M main
git remote add origin git@github.com:USERNAME/yomi.git
git push -u origin main
```

Ветки: `main` всегда собирается и проходит тесты. Работа — в ветках
`feat/чтение-cbz`, `fix/сортировка-страниц`.

## Формат коммитов

[Conventional Commits](https://www.conventionalcommits.org/ru/): по префиксу
понятно, что изменилось, и из истории автоматически собирается CHANGELOG.

```
feat: чтение CBZ-архивов
fix: страницы сортировались лексикографически, 10 шла раньше 2
docs: раздел про tmux в nixos.md
refactor: вынести определение формата в отдельную функцию
test: интеграционные тесты кодов возврата
chore: обновить зависимости
```

Тело коммита пишите, когда решение неочевидно: **что** сделано видно
из diff, а вот **почему** — нет.

## Версии

Семантическое версионирование. До 1.0 ломающие изменения допустимы
в минорной версии — проект молодой, интерфейс ещё устаканивается.

Выпуск: обновить `CHANGELOG.md`, поднять версию в корневом `Cargo.toml`
(она общая для всех крейтов), поставить тег `v0.2.0`.

## Когда что-то не собирается

1. Прочитайте ошибку целиком — в Rust в конце обычно лежит решение.
2. `rustc --explain E0502` — развёрнутое объяснение по коду ошибки.
3. `cargo clean` помогает редко, но если помогло — значит, попортился кэш.
4. Раздел «Что делать, когда компилятор ругается» в [rust-primer.md](rust-primer.md).

## Работа с Claude Code

Для этого проекта удобнее веб-чата: есть доступ к файлам, можно запускать
тесты и коммитить. Полезные привычки:

- Держите в репозитории `CLAUDE.md` с кратким описанием проекта и правилами —
  он подхватывается автоматически в начале сессии.
- Просите **сначала показать план**, потом писать код: так дешевле
  исправлять недопонимание.
- Формулируйте задачу вертикальным срезом: не «сделай модуль viewer»,
  а «показать одну картинку в kitty и выйти».
- После каждого блока работы — `cargo test` и коммит. Мелкие коммиты
  проще откатывать.
- Git — механизм преемственности между сессиями: контекст теряется,
  история изменений остаётся.
