# ADR-0002. Разделение на `yomi-core` и `yomi`

## Контекст

На этапе M4 появится TUI, а в перспективе возможен фоновый демон. Если
логика перемешана с печатью в терминал, каждый новый интерфейс потребует
её дублировать.

## Решение

Два крейта в одном рабочем пространстве. `yomi-core` — доменная модель,
конфигурация, источники, никакого ввода-вывода в терминал. `yomi` —
разбор аргументов, форматирование, коды возврата. Зависимость строго
в одну сторону.

## Альтернативы

**Один крейт с модулями.** Проще на старте, но границу нечем удержать:
ничто не мешает вызвать `println!` из логики, и через полгода
разделение станет неподъёмным.

**Крейт на каждый модуль** (`viewer`, `db`, `downloader` отдельно).
Избыточно для проекта такого размера: растёт время сборки и число
`Cargo.toml` без выигрыша.

## Последствия

Граница проверяется механически: появление `use clap` или `println!`
в `yomi-core` — сигнал о нарушении. Ядро тестируется без запуска
процесса. Ценой — чуть больше церемоний при добавлении публичного типа.
